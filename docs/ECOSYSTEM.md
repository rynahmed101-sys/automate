# Mathematical Physics Software Ecosystem & Automate Interoperability

**Date**: 2026-10-03  
**Status**: Architecture Reference  
**Core Principle**: Automate is an interoperability and derivation layer. Do not duplicate or compete with specialized theorem provers, computer algebra systems, or empirical regression tools.

---

## 1. Ecosystem Survey

### 1.1 Physics Derivation Graph (PDG)
* **Author / Organization**: Ben Payne (`allofphysicsgraph`, allofphysics.com)
* **Purpose**: Document every mathematical step in theoretical physics as a directed property graph.
* **Representation**: Neo4j property graph, LaTeX expressions, Python AST parser, web interface.
* **Strengths**: Extensive taxonomy of physics inference rules (hundreds of documented transformations), community effort to map physics from axioms to predictions.
* **Relevant Interfaces**: Graph schema, rule catalog (e.g. `add_x_to_both_sides`, `differentiate_wrt`, `substitute`), CSV/JSON exports.
* **Licensing**: Creative Commons Attribution 4.0 / GPLv3.
* **What Automate Should Reuse**:
  - The concept of machine-readable inference rules with explicit input/output expressions.
  - The catalog of physical transformation names and classifications.
* **What Automate Should NOT Duplicate**:
  - Do not copy the full web UI or Neo4j server backend.
  - Automate focuses on multi-backend active verification (Lean + SymPy + SciPy) rather than purely archival graph storage.

---

### 1.2 Physlib (formerly HEPLean & Lean-QuantumInfo)
* **Organization**: `leanprover-community/physlib` (physlib.io)
* **Purpose**: Foundational library for formalizing physics in Lean 4 ("Mathlib for physics").
* **Representation**: Lean 4 inductive types, structures, and Mathlib-compatible proofs.
* **Strengths**: Rigorous type-theoretic formalizations of spacetime manifolds, quantum states, Lorentz symmetry, and particle physics representations.
* **Relevant Interfaces**: Lean 4 packages imported via `lakefile.lean`.
* **Licensing**: Apache-2.0.
* **What Automate Should Reuse**:
  - Target formal proof obligations generated by Automate directly into Physlib/Lean 4 definitions.
  - Use Physlib's conventions for physical units, spacetime dimensions, and conserved currents.
* **What Automate Should NOT Duplicate**:
  - Automate does not formalize differential geometry or quantum mechanics in Lean from scratch.
  - Automate acts as the compiler/orchestrator that generates the obligations for Physlib to prove.

---

### 1.3 physicslib4 & Lean4PHYS
* **Organization**: Lean4PHYS research team / Peking University
* **Purpose**: Benchmark and reasoning framework for formal physics in Lean 4 (including `LeanPhysBench` with 200 college-level physics problems).
* **Representation**: Lean 4 code with problem statements, theorems, and solutions.
* **Strengths**: Standardized representation of college-level physics problem formulations in Lean 4; benchmark for AI-driven formalization.
* **Relevant Interfaces**: Problem datasets, Lean 4 formalization templates.
* **Licensing**: Open Research / Apache-2.0.
* **What Automate Should Reuse**:
  - Benchmark problem structures and proof patterns for classical mechanics and electrodynamics.
* **What Automate Should NOT Duplicate**:
  - Do not duplicate the benchmark runner; rather, enable Automate to parse and check benchmark problems.

---

### 1.4 Mathlib (Lean 4)
* **Organization**: `leanprover-community/mathlib4`
* **Purpose**: The de facto unified mathematical library for Lean 4.
* **Representation**: Formal mathematics in dependent type theory (Calculus, Topology, Algebra, Analysis).
* **Strengths**: Thousands of formalized lemmas, tactics (`ring`, `linarith`, `norm_num`, `aesop`), continuous calculus foundations.
* **Relevant Interfaces**: Lean 4 compiler (`lean`, `lake`).
* **Licensing**: Apache-2.0.
* **What Automate Should Reuse**:
  - Automatic tactic dispatching (`linarith`, `ring`, `simp`) for algebraic side conditions.
* **What Automate Should NOT Duplicate**:
  - Never reimplement algebraic structures, real analysis, or group theory; delegate all formal proof checking to Mathlib.

---

### 1.5 Get Physics Done (GPD) / Formal Physics Initiatives
* **Purpose**: Pragmatic computational workflows for theoretical physicists bridging symbolic manipulation and notebook computing.
* **Representation**: Python, Jupyter notebooks, SymPy scripts.
* **Strengths**: Ease of use for practicing physicists, low barrier to entry.
* **Relevant Interfaces**: Python API, SymPy lambdify, NumPy array pipelines.
* **Licensing**: Open Source (MIT/BSD/Apache).
* **What Automate Should Reuse**:
  - Human-friendly input formats (YAML theory files) that feel natural to theoretical physicists.
* **What Automate Should NOT Duplicate**:
  - Avoid unstructured, unverified notebook state; enforce DAG provenance and explicit assumptions.

---

### 1.6 PIR (Physics Intermediate Representation) & Physics Engines
* **Purpose**: Domain-specific intermediate representations for simulation, symbolic regression, and physical dynamics.
* **Representation**: ASTs with dimensional tags and operator graphs.
* **Strengths**: Fast evaluation, clear AST node semantics.
* **Relevant Interfaces**: JSON/YAML AST schemas.
* **What Automate Should Reuse**:
  - Canonical expression serialization schemas with explicit dimensional analysis.
* **What Automate Should NOT Duplicate**:
  - Do not become a real-time game physics or graphics engine.

## 2. Automate's Distinct Role: The Interoperability Layer

Automate provides the **common representation** and **verification orchestration** connecting these systems. Backends and tools are pluggable and replaceable; the derivation DAG and its machine-readable certificates are permanent.
